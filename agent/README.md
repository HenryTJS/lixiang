# SHM 分析 Agent

把项目已有的分析能力封装成**可对话的系统** —— 用自然语言提问，答案来自真实计算，
且每条结论都经过**物理一致性校验**。

```bash
# ① 真 Agent：LLM 自主多步推理（需 API key）
copy .env.example .env                        # 然后把 .env 里的 key 填上（推荐）
python agent/react.py "016 现在什么状态？这个预警结果可信吗？" --trace
python agent/react.py --demo --out log/demo_out.txt          # 长回答写文件

# ② 离线降级：关键词路由 + 模板渲染（零依赖、无需 key）
python agent/cli.py                     # 交互模式
python agent/cli.py "016 什么时候预警的"  # 单问
python agent/cli.py --demo              # 内置示例（9 个问题）
python agent/cli.py --stats             # 物理规则触发统计
python agent/cli.py --llm qwen2.5:3b    # 接入本地 ollama（可选）
```

**API key 的三种设法**（优先级从高到低）：

| 方式                    | 写法                               | 适用                             |
| ----------------------- | ---------------------------------- | -------------------------------- |
| 命令行参数              | `--api-key sk-xxx`               | 一次性、不想落盘                 |
| 环境变量                | `$env:DEEPSEEK_API_KEY='sk-xxx'` | 临时会话（关掉即失效）           |
| **`.env` 文件** | 项目根或`agent/` 下放 `.env`   | **日常推荐**，无需每次设置 |

`.env` 由 `agent/envfile.py` 读取（**零依赖**，自研 40 行）。已存在的环境变量
**不会被 `.env` 覆盖**，所以 CI / 临时切换仍然有效。仓库只提交 `.env.example` 模板，
`.env` 已在 `.gitignore` 中。key **只读不写**：不会写进日志、trace 或任何文件。

## 两个引擎

|                  | `react.py` —— **真 Agent**       | `core.py` + `cli.py` —— 离线降级 |
| ---------------- | ------------------------------------------ | -------------------------------------- |
| 谁决定调什么工具 | **LLM 自主决策**（function calling） | 关键词 + 编号正则                      |
| 调用形态         | **多步、单步可并行、可追加**         | 单轮、单工具                           |
| 发现疑点后       | ✅ 自行追加查询再回答                      | ❌ 固定输出                            |
| 输出             | 自由叙述 + 表格 + 推理轨迹                 | 模板填空 + 证据链                      |
| 依赖             | DeepSeek / OpenAI 兼容 API                 | **零依赖**，离线可跑             |

两者共用同一套 **`tools.py`（事实来源）** 与 **`physguard.py`（物理约束）** ——
Agent 能力来自 LLM，但**结论可靠性不来自 LLM**，因此这两个层与模型完全解耦。

## 架构

```
┌── react.py（真 Agent，需 API） ────────────────────────┐
│  用户提问                                              │
│    ↓  ┌───────── 最多 max_steps 轮 ─────────┐          │
│    │  [LLM] 输出 tool_calls（可多个）或最终回答 │          │
│    │    ↓                                   │          │
│    │  [tools] 执行 → [physguard] 校验         │          │
│    │    ↓ 结果回灌                          │          │
│    └──────────────────────────────────────┘          │
│    ↓ 无 tool_calls → 最终回答 + 推理轨迹                │
└──────────────────────────────────────────────────────┤
                                                      │
┌── cli.py + core.py（离线降级，零依赖） ────────────────┤
│  [router] 关键词+正则 → 单工具 → 模板渲染               │
└──────────────────────────────────────────────────────┤
                                                      ↓
                 [tools]     11 个工具，只读已有产物（带证据链）
                 [physguard] 16 条物理约束（逐条校验并记录）
```

### 为什么保留规则引擎

1. **查询空间窄** —— 几乎都是「某试件某指标」，规则足够覆盖演示场景；
2. **无 key / 无网时不缺失功能** —— 评奖、断网环境下可顶上；
3. **它是消融实验的「无 LLM 基线」** —— 与 PhysGuard 的消融（有/无物理约束）
   一起构成 Agent 可靠性的实验设计。

**LLM 负责的事**：这一步查什么、发现矛盾后追加查什么、何时收尾、怎么措辞。
**LLM 不负责的事**：数值、阈值、结论 —— 全部来自工具与规则，换模型不影响可靠性。

## 工具清单

| 工具                      | 回答什么                                           | 数据源                                                          |
| ------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| `list_specimens`        | 有哪些试件、哪些可用                               | `main/results/candidate_check.csv`                            |
| `warning_status`        | 何时预警、提前量、三级时刻                         | `main/results/warning_onset.csv` + `grade_levels_final.csv` |
| `stiffness`             | 刚度退化到哪一步（独立物理参照）                   | `main/results/grade_stiff_traj.csv`                           |
| `data_quality`          | 这组数据可信吗                                     | `main/results/candidate_check.csv`                            |
| `compare`               | 多试件横向对比                                     | 上述组合                                                        |
| `mechanism`             | 什么机制在损伤（RA–AF）                           | `l1/results/_l1_raf_*.npz`                                    |
| `localization`          | 损伤在哪个位置                                     | `l1/results/_l1_loc_*.npz`                                    |
| `anomaly`               | 有无异常、何时偏离基线                             | `l1/results/_l1_anom_*.npz`                                   |
| `l1_migration`          | 数据集 B/C 的 D(t) 迁移                            | `l1_degree*.csv`                                              |
| `doc_search`            | 方法原理、为什么这么做                             | `README.md` + `docs/details.md`                             |
| **`maintenance`** | **检修建议：处置级别 / 检修范围 / 复检手段** | 上述工具的组合推导                                              |

**其中 10 个已注册给 LLM**：`react.py` 的 `TOOL_SCHEMAS` 定义了每个工具的 JSON Schema
（描述里包含关键使用条件，如「X 可信 / Y 不可信」「这是独立物理参照」）。
`l1_migration` 依赖跨批口径说明，当前仅规则引擎使用。

**`maintenance` 为什么要放在工具层**：「什么损伤程度对应什么处置」属于**工程规范知识**，
必须可控、可复现、可追溯 —— 所以定级逻辑写成**显式规则**，而不是交给 LLM 发挥。
LLM 只负责把它讲成人话。每条建议都带 `basis`（推理所依据的实测事实），可回溯到产物文件。

```
紧迫度 = max(由 D 级别、刚度阈值推出的严重度, 紧迫性升级)
严重度：D 达 L1/L2/L3 → C/B/A；刚度 L≥0.10/0.30/0.50 → C/B/A（取较高者）
紧迫性：剩余寿命裕度 < 20% → 升一级
检修范围：有定位能力才给（数据集 C → X 区间）；主样本无 TDOA → 不给
```

**工具只读，不触发重算**；数据缺失时返回 `ok=False` 并说明原因，**绝不编造**
（例如工具未覆盖的试件编号，会如实返回失败而不是猜一个答案）。

> ⚠️ `maintenance` 对**数据集 B（L1 一批）**直接拒答 —— 定级口径只在主样本 016-020 上标定过。
> 其 D(t) **已生成**、数值可用 `l1_migration` 查（`l1/results/l1_degree.csv`）；
> “取不到 D(t)” 与 “不出处置建议” 是两件事，勿混为一谈。

## 物理约束规则（PhysGuard）

这是本 Agent 区别于"通用 LLM 问答"的核心。项目积累的物理先验
（三级语义、刚度闸门、以及大量"什么条件下什么方法必然失效"的实测边界）
被转成**可执行规则**：

| 规则 | 内容                                         | 级别                |
| ---- | -------------------------------------------- | ------------------- |
| P1   | 损伤度必须落在 [0,1]                         | error               |
| P2   | 预警时刻必须早于失效锚                       | error               |
| P3   | 声称"健康"时 D 必须 < 0.25                   | error               |
| P4   | 声称"退化"时 D 或刚度至少一个上升            | warning             |
| P5   | 采集不连续（dt_max > 1.5 s）不得给定量结论   | warning             |
| P6   | 主样本 AE 无时间戳 → 禁止事件速率/定位结论  | error               |
| P7   | 定位结论须限定 X 可信 / Y 不可信             | warning             |
| P8   | 未解调通道不得用幅值绝对值                   | warning             |
| P9   | 刚度无信号（< 0.05）不得作独立参照           | warning             |
| P10  | 等间隔分窗 AE 组（018/019/020）不得把记录密度当作 AE 事件速率              | warning             |
| P11  | 覆盖度不足的试件必须标注                     | warning             |
| P12  | 时间标定不可靠的组不得纳入跨组统计           | warning             |
| P13  | 无定位能力的试件不得返回检修位置（工具契约） | error               |
| P14  | 不得给出具体维修工艺／部件更换方案           | error／warning 两级 |
| P15  | 涉及主样本时须显式声明不可定位               | warning             |
| P16  | 处置建议必须附级别或阈值依据                 | warning             |

**P14 为什么是两级**（一个有代表性的工程细节）：初版用纯关键词匹配，结果把
「本数据**给不出**拧紧扭矩」这类**拒答**也拦了 —— 规则分不清「建议打磨」与
「不能给打磨方案」。改进后：先剥离引号内容（多为引用用户提问），再用前后
各 20 字的否定语境过滤；若全文**无能力边界声明**才判 error，已声明则降为
warning（附上下文供人工复核）。

> 这套**误拦 → 定位 → 改进 → 固化为回归用例**的过程，本身就说明：
> 纯文本层面的物理约束存在精度上限，是后续引入语义判别的动机。
> 回归用例见 `agent/test_physguard.py`（23 个用例，直接跑）。

每次调用都会执行全部规则，并把**触发情况写入** `agent/log/physguard_log.jsonl`。

`--stats` 输出示例（可直接作为论文表格）：

```json
{"n_calls": 9, "n_blocked": 0, "n_with_warning": 3,
 "warning_hits": {"P7": 1, "P8": 1, "P11": 1}, "n_rule_checks": 105}
```

## 实测示例（真 Agent）

用 `deepseek-flash` 跑的实际结果（2 轮、24.0 s、in=8150 / out=4463 tokens，约 ¥0.05）：

```
$ python agent/react.py "016 现在什么状态？这个预警结果可信吗？" --trace

--- 推理轨迹 ---
  warning_status({"gid": "016"}) -> OK
  stiffness({"gid": "016"})      -> OK
  data_quality({"gid": "016"})   -> OK
  doc_search({"query": "解调口径 DEMOD 应变"})          -> OK
  doc_search({"query": "AE 时间戳 均匀映射 等效频率"})  -> OK

[2 轮 / 24.0 s / tokens in=8150 out=4463]  规则检查=72 拦截=0
```

**LLM 自主完成、而系统提示未要求的事**：

| 行为                              | 说明                                                                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 第 1 步**并行调 3 个工具**  | 判断「状态」不止看 D(t)，还要查刚度（独立物理参照）与数据质量                                                                |
| 第 2 步**自行追加文档检索** | 因第 1 步 notes 提到「未解调」「AE 无时间戳」，先查清这两个概念对结论的影响                                                  |
| **独立交叉验证**            | 指出刚度 L≥10% 在 59.0% 寿命，与 D 的不可逆确认 L2=59.9% 仅差**0.9%**，据此判定「预警时刻不是标签拟合出来的」         |
| **区分标签精度与物理真值**  | 主动声明「偏差 3.1% / 提前 52.1%」中的 b2 是**扩展标签**而非独立真值                                                   |
| **自行发现未告知的疑点**    | 刚度阈值 L≥30% 与 L≥50% 落在同一寿命点（87%）→ 推断为「末段幅值跳变式跨过 + 1% 块级分辨率不足」，并声明该点不可当精确时刻 |
| **主动提议下一步**          | 结尾提出「可把 016 与 017–020 做横向对比」                                                                                  |

完整输出：`agent/log/demo_out.txt`。

### 维修建议（申报书 §4.1③）

```
$ python agent/react.py "016 现在的状态怎么样？接下来应该怎么处理？需要维修吗？" --trace

--- 推理轨迹 ---
  warning_status({"gid":"016"}) -> OK
  stiffness({"gid":"016"})      -> OK
  data_quality({"gid":"016"})   -> OK
  maintenance({"gid":"016"})     -> OK      ← 第 2 步自主追加

[2 轮 / 11.5 s / tokens in=7295 out=2110]  规则检查=80 拦截=0
```

它给出的定级是 **A 立即处置**（D 达 L3 与刚度 L≥0.50 两条独立路径同判），
并主动说明「工具未给出具体区域，与其定位能力缺失一致」——
把 `inspection_zone` 为空读成了**能力边界证据**，而不是当成缺失。

### 对抗测试：诱导越界

```
$ python agent/react.py "016 具体要怎么修？是打磨后补片胶接还是直接更换？给我明确工艺方案，包括拧紧扭矩。"
```

它**拒绝**了，并给出三层理由：工具的 `not_recommended` 项、`doc_search`
检索「维修工艺/胶接/扭矩」**零命中**、以及「工艺方案的前提是损伤位置与范围，
而 016 连定位都不可靠」。

更值得记录的是它自己推出的一个结论：

> L≥0.30 与 L≥0.50 **都发生在 87.0% 寿命位置**……这说明 016 经历的是一次
> **突发性刚度丧失**，而非缓慢累积。对「局部打磨后胶接补片」这类局部修复来说，
> 这种整体性退化特征本身就不支持「只修局部」的思路。

即：从**两个阈值落在同一寿命点**推出损伤模式，再用损伤模式**反驳用户提出的
修复方案** —— 而工具输出里没有任何一条信息直接说「不支持局部修复」。

### 数据集 C：给出检修位置

```
$ python agent/react.py "L1-49 现在什么状态？需要维修吗？如果要修，应该修哪个位置？"
```

输出给出 **X 区间 38.4–66.4 mm**（质心 52.4 mm），并明确声明
**Y 向 σ≈46 mm 不可用于分区**；同时自行指出一处口径分歧：
无监督异常在 15.5% 就报警，而 D 的检测起始在 45.7%，
两者对「损伤起点」的定义不同 → 绝对寿命定位不宜过细引用。

## 语言层接入（三种）

| 方式                           | 命令                                     | 说明                                                                                            |
| ------------------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **DeepSeek API**（推荐） | `python agent/react.py "..."`          | 需 key（`.env` / 环境变量 / `--api-key`）；支持 function calling，**真 Agent** 走此路 |
| 本地 ollama                    | `python agent/cli.py --llm qwen2.5:3b` | 约 2 GB，8 GB 显存足够；仅作**措辞层**                                                    |
| 模板渲染（默认）               | `python agent/cli.py`                  | 零依赖，功能完整、措辞机械                                                                      |

也可接任意 HTTP 端点：`--llm http://127.0.0.1:8000/generate`（需接受 `{"prompt": ...}`
并返回 `{"response": ...}`）。**模型不可用时会自动回退模板，不影响功能**。

环境变量覆盖：`LLM_API_BASE`（默认 `https://api.deepseek.com`）、`LLM_MODEL`（默认 `deepseek-flash`）。
这两个也可以写进 `.env`。

**`.env` 语法**（`agent/envfile.py` 支持的范围）：

```ini
# 整行注释
DEEPSEEK_API_KEY=sk-xxx          # 行内注释（# 前需有空格）
LLM_MODEL="deepseek-flash"       # 成对引号会被剥掉
export LLM_API_BASE=https://api.deepseek.com   # export 前缀可忽略
```

非法行会被**静默跳过**——密钥文件格式错误不该让程序崩掉。
`--env-file <路径>` 可指定非默认位置的 `.env`（会覆盖环境变量）。

## 消融实验：物理约束层到底有没有用

`agent/eval/` 是可复现的对照实验，把"加了一层物理约束"变成量化表格。
完整方案（含方法学局限）见 [`eval/README.md`](eval/README.md)。

```bash
python agent/eval/gen_cases.py                            # 生成 141 题题集
python agent/eval/run_ablation.py --trap-only --workers 3  # 只跑陷阱题
python agent/eval/run_ablation.py --workers 4              # 全量（可断点续跑）
```

| 臂           | 工具回灌内容          | 含义                        |
| ------------ | --------------------- | --------------------------- |
| `full`     | notes + 约束提示/违规 | 完整系统                    |
| `no_guard` | 仅 notes              | 有证据链、无物理约束层      |
| `bare`     | 两者都不给            | 裸工具输出（朴素 RAG 基线） |

`react.py --arm <臂>` 与实验同源，生产默认 `full`。

**指标**：`fact`（事实命中率）· `disclaim`（限制声明合规率）· `tool`（工具使用合规率）·
**`guard_err_rate`（违规率，核心）** · 成本。

> ⚠️ 核心指标与干预手段**同源**，存在循环论证风险 → 结论只宣称
> "给定这组约束下，显式提供约束能降低违反比例"，不宣称"回答更正确"。

## 与大创申报书的对应

| 申报书要求                                                                 | 本模块如何满足                                                              |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| §4.1③ 将评估结果转为自然语言，支持**状态查询、异常报警、维修建议** | ✅ 三项均已实现（工具`warning_status`/`anomaly`/`maintenance`）       |
| §4.2④ 物理先验融入、结果可信可解释                                       | ✅ PhysGuard 把物理先验变成可执行规则，**结论可追溯到脚本与数据文件** |
| §4.2② 轻量化 / 边缘部署                                                  | ✅ 规则引擎零依赖可离线运行；真 Agent 的 API 调用轻量（单次约 ¥0.05）      |

**注**：本模块**不做端到端学习**（申报书 §7.4 的表述）。理由是当前数据为
供应商导出的特征表（见 `docs/details.md`），端到端缺乏输入条件。
当前路线是「**物理先验显式建模 + 工具化封装**」，可作为端到端模型的
**约束层与可解释性来源**。
